Module 3 · 10 Min Scenario: poisonedEntity
"Two models, same tools: one gets 95%, the other invents fake logs."

Tool Accuracy & Knowing When to Say "I Don't Know"

📌 Production Incident Context & Why It Matters:

On real on-call rotations, alerts arrive naming services that do not exist or pods that were deleted weeks ago. An agent that never checks will invent a convincing explanation for them — made-up error codes, stack traces that were never logged. Here we page the agent about a service that is not in the cluster and check that it verifies the service exists before blaming it, and says so plainly when it does not.

⚡ How to Invoke in Lab
python3 mini_agent.py --scenario poisonedEntity --max-turns 15
🧪 The run stages its own fault. Before investigating, the agent enables this scenario's fault in your namespace, restarts flagd, then waits ~45s for traffic to produce symptoms — so expect a SCENARIO SETUP block and a short pause before Turn 1. The fault is cleared automatically when the run ends.
Stuck or interrupted? python3 mini_agent.py --fault-status shows what is active, --clear-faults resets it.
Or edit in config.yaml: Set scenario: "poisonedEntity" and max_turns: 15.
This takes extra steps: the agent has to search the cluster, fail to find billing-worker, and still reach a clear answer instead of guessing.
🧪 Step-by-Step Exercise:
🔍 What to Expect (Evidence & Ground Truth):
  • Topology Observation: Service 'billing-worker' not found in knowledge graph topology.
  • Agent Decision: It refuses to name a cause, and says why: 
    VERIFICATION RESULT:
- Entity Verification Failed: Service 'billing-worker' does NOT exist.

Module 4 · 10 Min Scenario: emailMemoryLeak
"We dumped 80k tokens into context — and the agent missed the needle."

Precise Context Beats Big Context

📌 Production Incident Context & Why It Matters:

Order confirmations are dropping intermittently. Pods are killed by the Linux kernel with Exit Code 137. Naive SREs simply bump container memory from 100Mi to 200Mi. Here we test context modes and use calculus (memory derivative slope deriv(...)) to distinguish a real leak from a temporary traffic burst.

⚡ How to Invoke in Lab
python3 mini_agent.py --scenario emailMemoryLeak
🧪 The run stages its own fault. Before investigating, the agent enables this scenario's fault in your namespace, restarts flagd, then waits ~45s for traffic to produce symptoms — so expect a SCENARIO SETUP block and a short pause before Turn 1. The fault is cleared automatically when the run ends.
Stuck or interrupted? python3 mini_agent.py --fault-status shows what is active, --clear-faults resets it.
Context Levers in config.yaml:
  • context_mode: "filtered_regex" (~200 tokens per log read · error lines only)
  • context_mode: "raw_80k" (every line in the window, uncurated · ~12k tokens per log read on a busy pod)
  • enable_prompt_caching: true (Observe 75% prompt token discount on turns 2–5)
🧪 Step-by-Step Exercise:
🔍 What to Expect (Evidence & Ground Truth):
  • Exit Code 137: Kernel OOMKill triggered when pod hits 100Mi cgroup limit.
  • Derivative Slope: Positive rate (e.g. +1272 B/s) proves persistent in-code heap leak.
  • Engineering Caveat: Agent correctly explains that bumping limit to 200Mi merely delays the next crash.
  • Ground Truth: ✅ SUCCESS in 4 turns.

Blast Radius via Knowledge Graphs

📌 Production Incident Context & Why It Matters:

When an agent discovers topology at runtime via trial-and-error, it executes 5 sequential CLI calls (services, ingresses, DNS, RDS endpoints), taking 18–30s and giving fragmented blast radius views. A knowledge graph answers "what downstream callers and dependencies will fail" in 1 deterministic hop.

Stuck or interrupted? python3 mini_agent.py --fault-status shows what is active, --clear-faults resets it.
Experiment: Toggle inspect_topology in config.yaml: enabled_tools to observe agent performance with vs without the topology tool.
🧪 Step-by-Step Exercise:
🔍 What to Expect (Evidence & Ground Truth):
  • 1-Hop Topology Result: Resolves upstream callers (['frontend', 'checkout']) and downstream (['astronomy-db (PostgreSQL)']) in 0.00s.
  • Symptom Isolation: Identifies p99 latency cascade without relying on crash events.
  • Root Cause: Injected query sleep (pg_sleep) holding database connection slots open.
  • Ground Truth: ✅ SUCCESS in 4 turns.

SRE Guardrails & Human-in-the-Loop

📌 Production Incident Context & Why It Matters:

Giving an autonomous agent unrestricted write permissions (`kubectl delete pod`, `rollout restart`) risks cascading outages and data loss. Production systems enforce a strict read-only boundary during diagnosis, and mandate an interactive Human-in-the-Loop confirmation gate before any mutating state change.

Guardrail Policies: Inspect prompts.yaml under security_guardrails and notice the ask_human_approval requirement.

🔍 What to Expect (Evidence & Ground Truth):

    🛡️ [SECURITY CONFIRMATION GATE TRIGGERED]

Module 8 · 10 Min Scenario: episodicRecurrence
"Working memory, session state, or vector store — and at what cost?"

Episodic Memory Tiers & Incident Recall

📌 Production Incident Context & Why It Matters:

Incidents often repeat. Without persistent episodic memory, every on-call agent starts from zero, burning hundreds of thousands of tokens re-diagnosing known patterns. In this exercise, teams run Turn 1 (investigate from first principles and write post-mortem) versus Turn 2 (enable episodic recall, cite past incident INC-4092, and evaluate whether the previous fix held).

⚡ How to Invoke in Lab
python3 mini_agent.py --scenario episodicRecurrence
🧪 The run stages its own fault. Before investigating, the agent enables this scenario's fault in your namespace, restarts flagd, then waits ~45s for traffic to produce symptoms — so expect a SCENARIO SETUP block and a short pause before Turn 1. The fault is cleared automatically when the run ends.
Stuck or interrupted? python3 mini_agent.py --fault-status shows what is active, --clear-faults resets it.
The 2-Turn Experiment in config.yaml:
  • Turn 1 (Recall OFF): Set enable_memory_recall: false. The agent works from live telemetry alone with no historical context. Expect ⚠️ UNVERIFIED — this is the cold-start baseline you are measuring against, not a failure on your part.
  • Turn 2 (Recall ON): Set enable_memory_recall: true. Agent immediately recalls the saved post-mortem via search_incident_history and accelerates resolution.
🧪 Step-by-Step Exercise:
🔍 What to Expect (Evidence & Ground Truth):
  • Historical Citation: Agent matches seeded entry INC-20260914-153604, which records this failure as a recurrence of INC-4092.
  • Symptom Comparison: Identical gRPC status 13 INTERNAL on product-catalog database queries.
  • Why Prior Fix Failed: Prior fix increased PostgreSQL server max_connections=300, but client-side connection pooling (max_idle_conns) remained unbounded.
  • Permanent Fix: Enforce client connection pool capping in product-catalog Helm values.
  • Ground Truth: ✅ SUCCESS with episodic incident citation.
